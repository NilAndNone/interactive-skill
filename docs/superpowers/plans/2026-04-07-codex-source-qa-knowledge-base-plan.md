# 面向 Codex 的源码问答知识库初步方案

> 适用对象：`Codex`、后续具备深度检索能力的强模型、负责维护知识库的人类研究员
> 文档定位：本文件是知识库方案文档，不是实现说明，不要求直接写代码、做补丁或交付功能
> 参考框架：Karpathy `LLM Wiki` 思路，原文链接为 `https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f`

## 一、任务目标

围绕 `Claude Code` 与 `Codex` 两份源码及其配套官方材料，建立一套主要供 `Codex` 读取和使用的源码问答知识库。该知识库的首要目标不是覆盖所有源码实体，而是稳定回答以下两类问题：

- 日常高频问答：某个机制如何工作、边界在哪里、某配置或能力会影响什么
- 面试问答：设计动机是什么、架构如何取舍、不同机制之间如何比较、某条结论是否能被源码支持

本方案的核心要求如下：

- 让 `Codex` 回答前先读知识库，而不是每次重新从源码全量搜索
- 每个稳定结论都能回到源码或官方材料
- 事实、推导和猜测必须明确分层
- 首版优先可读、可答、可追溯，不优先追求重型知识图谱化

## 二、首版定位

### 1. 本库是什么

本库是一个面向 `Codex` 外部读取的源码问答知识库。它不是单纯的源码摘要仓库，也不是先天面向自动化检索的 RAG 素材库，而是位于“原始材料”和“最终回答”之间的一层结构化中间层。

这层中间层的主资产是标准化问答卡片。`Codex` 在回答问题时，应优先读取这些卡片，再按需要回看源码锚点和官方材料。

### 2. 本库不是什么

首版不应被设计成以下形态：

- 不做“通用个人 wiki”
- 不做“全量源码实体百科”
- 不做“重型法证式 claim/trace/patch 全覆盖系统”
- 不默认依赖向量检索、RAG 或复杂工具链

### 3. 首版目标形态

首版推荐采用：

- 问题域组织
- 问答卡片作为标准回答单位
- 轻量源码锚点层作为证据补充层

也就是说，首版应采用“问题域问答卡片主库 + 轻量源码锚点层”的结构，而不是直接进入重型源码知识工程。

## 三、核心原则

### 1. 问答优先

首版的主资产必须是能直接回答问题的卡片，而不是覆盖所有函数、类、模块的全面实体页。

### 2. 问题域优先

页面应按未来会反复提问的问题域组织，而不是按源码目录树组织。源码目录树适合作为证据回溯路径，不适合作为首要导航方式。

### 3. 证据可回溯

每张卡片都必须能回到源码位置、官方文档、提交记录或 issue / PR。没有证据锚点的稳定结论，不应进入正式卡片。

### 4. 轻量建模

首版不强制全量建设 `entity / trace / claim / patch` 页面。只有当某问题存在高争议、高复杂度、强版本相关性或高复用价值时，才下沉到锚点页。

### 5. 确定性分层

所有正式回答和所有正式卡片都必须显式使用以下三层：

- `confirmed`
- `derived`
- `hypothesis`

不得把推断写成源码已确认事实。

## 四、事实边界与来源分层

### 1. 核心事实源

首版知识库的核心事实源包括：

- `Claude Code` 源码快照
- `Codex` 源码快照
- 官方文档
- 官方提交记录
- 官方 issue / PR

其中，源码快照仍然是最强证据锚点。官方材料可用于解释设计意图、版本演进和行为约束，但不应替代源码对运行机制的直接说明。

### 2. 外部材料的角色

外部文章、帖子、访谈、二手分析可以被收集，但其角色应被限定为：

- 提供问题线索
- 提供验证方向
- 提供术语和比较角度

这类材料不应直接升格为 `confirmed` 事实。

### 3. 三层确定性定义

#### `confirmed`

直接由源码、官方文档、官方 issue / PR 或可复核实验支持的结论。

#### `derived`

由多个 `confirmed` 事实综合推导出的解释或判断。

#### `hypothesis`

暂未被足够证据支持、但具有讨论价值的推测、猜想或待验证观点。

## 五、知识库总体结构

首版建议保留 Karpathy 框架的三层骨架，但按问答目标收窄。

### 1. `raw/`

用于存放不可改写的输入材料，包括：

- 源码快照
- 官方文档摘录
- 提交记录、issue / PR 摘录
- 外部参考材料

这里的材料默认只读，不允许把知识整理结果直接写回本层。

### 2. `wiki/`

这是首版的主工作层。该层应以问题域问答卡片为核心，并保留少量导航和证据页。

建议至少包含：

- `index.md`
- `log.md`
- 按问题域组织的问答卡片目录
- `anchors/` 作为复杂锚点页目录

### 3. `schema/`

用于存放知识库使用规则，而不是写成一大坨常驻指令。首版应包括：

- 卡片模板
- 证据分层规则
- 回答流程规则
- 更新流程规则
- 命名与链接规范

## 六、一级问题域建议

首版不宜铺太多领域。建议先围绕你最可能反复提问的机制建立一级问题域：

- `skills`
- `plugins`
- `agents`
- `prompting`
- `runtime`
- `limits`
- `patchability`
- `comparison`

组织逻辑应始终围绕“将来会问什么”，而不是“源码里有什么目录”。

例如：

- `skills/how-are-skills-loaded.md`
- `skills/what-do-skills-change-at-runtime.md`
- `plugins/what-can-a-plugin-actually-change.md`
- `agents/who-controls-main-thread-agent.md`
- `comparison/claude-code-vs-codex-skill-model.md`

## 七、标准回答单位：问答卡片

首版的标准资产应是问答卡片，而不是泛化主题综述。

### 1. 单卡片只回答一个核心问题

每张卡片只回答一个核心问题。不得把“如何加载”“运行时影响”“影响边界”“可否 patch”混写在同一张大页中。

### 2. frontmatter 最小字段

每张卡片建议保留以下最小字段：

- `title`
- `domain`
- `question`
- `status`
- `sources`
- `last_verified`
- `related`

不建议首版加入过多机器字段，以免维护成本过早上升。

### 3. 正文固定六段

每张卡片建议固定使用以下结构：

#### `TL;DR`

用最短路径直接回答问题，优先服务日常问答。

#### `展开解释`

解释机制、边界、条件和例外，优先服务面试问答。

#### `证据锚点`

列出源码、官方文档、提交记录或 issue / PR 的定位信息。

#### `确定性分层`

显式列出哪些内容属于 `confirmed`、`derived`、`hypothesis`。

#### `延伸问题`

列出自然会继续追问的问题，方便 `Codex` 顺链读取。

#### `更新备注`

简要记录最近一次重要修订的原因，不把这部分写成长日志。

## 八、轻量源码锚点层

首版不强制全量建设重型锚点资产，但应预留一个轻量证据层，用于处理以下问题：

- 需要跨多个文件解释加载顺序
- 需要解释优先级、覆盖关系或副作用
- 需要分析版本差异
- 需要判断某个优化想法是否能通过改源码实现

此时再创建 `anchors/` 下的辅助页，例如：

- 复杂控制流页
- 高争议事实页
- 关键 patch 可行性页

这些页面的作用是为问答卡片提供下沉证据，而不是取代问答卡片成为主导航。

## 九、Codex 的标准问答工作流

首版必须给 `Codex` 一个稳定、可重复的问答流程。

### 1. 回答前流程

`Codex` 应按以下顺序处理问题：

1. 先读 `wiki/index.md`
2. 确定问题所属的问题域
3. 找到候选问答卡片
4. 读取目标卡片

### 2. 需要回源码核实的场景

如果问题涉及以下情形，则不能只停留在卡片层，必须继续回看源码或官方锚点：

- 加载顺序
- 调用链
- 优先级覆盖
- 运行时副作用
- 作用域边界
- 版本相关差异
- 源码可改点或 patch 可行性

### 3. 输出答案的固定结构

`Codex` 的正式回答建议固定包含以下部分：

- 直接结论
- 核心依据
- `confirmed / derived / hypothesis`
- 相关延伸问题

如果问题本身带有明显争议或不确定性，应在结论前直接声明不确定范围。

### 4. 回答后的回填原则

如果一次问答形成了稳定、可复用且能回到证据的新结论，该结论不应只留在聊天记录中，而应回填到知识库：

- 更新现有卡片
- 或新增一张卡片
- 或新增一个锚点页

这一步是知识库真正累积价值的关键。

## 十、更新与维护策略

### 1. 更新触发方式

首版采用快照驱动更新，而不是完全问答驱动。

也就是说，以下变化应触发正式更新：

- 新源码快照进入库中
- 官方文档出现重要更新
- 官方提交记录、issue / PR 出现显著变化

### 2. 更新时的最小动作

每次正式更新至少应完成：

- 更新相关卡片
- 补充或修正证据锚点
- 更新 `wiki/index.md`
- 追加 `wiki/log.md`

### 3. `log.md` 的作用

`log.md` 应是 append-only 记录，用于说明：

- 何时纳入了新快照
- 何时新增了重要卡片
- 何时修正了核心结论

它是时间线，不是内容目录。

## 十一、首版非目标

以下事项不应被纳入首版目标：

- 全量实体页建设
- 自动化 RAG / embedding 检索系统
- 大规模脚本化抽取与复杂注册表
- 全量 patch 提案体系
- 面向所有第三方外部材料的统一事实化处理

这些能力并非永远不做，而是首版不应让它们压过“可直接回答问题”这个核心目标。

## 十二、首批建设优先级建议

首版不应追求全覆盖，建议优先建设高频、高争议、高复用的问题。

建议优先从以下方向起步：

- `skills` 的加载方式与运行时影响
- `plugins` 实际能改变什么
- `agents` 如何决定主线程行为
- `prompting` 的优先级与覆盖关系
- `limits` 中哪些边界是源码硬限制，哪些只是提示层限制
- `comparison` 中 `Claude Code` 与 `Codex` 在技能、代理、插件或指令分层上的主要差异

这批问题最适合作为首版的骨架卡片集合。

## 十三、主要风险

### 1. 过度 FAQ 化

如果只写短答而缺乏证据锚点，知识库会快速退化成不可验证的 FAQ 堆。

### 2. 过度法证化

如果一开始就要求所有问题都下沉成复杂 `claim/trace/patch` 资产，首版会过重，影响建设速度和实际可用性。

### 3. 把外部讨论误写成事实

如果不严格区分外部材料的角色，就会污染知识库，使 `Codex` 在回答时错误提高确定性。

### 4. 页面颗粒度失控

如果单页混入多个核心问题，后续维护会越来越困难，`Codex` 也不容易稳定抽取答案。

## 十四、最终建议

综合首版目标、知识来源类型和 `Codex` 的实际使用方式，推荐采用以下路线：

- 以 Karpathy `LLM Wiki` 的 `raw/wiki/schema` 为骨架
- 以问题域组织知识库一级结构
- 以问答卡片作为首版主资产
- 以轻量源码锚点层承担复杂证据问题
- 以 `confirmed / derived / hypothesis` 作为统一确定性表达
- 以快照驱动更新主干内容
- 以 `index.md -> 问答卡片 -> 源码锚点` 作为 `Codex` 的固定阅读路径

这条路线的价值在于：

- 它足够轻，可以尽快开始积累高价值问答资产
- 它足够严，可以让 `Codex` 的回答保持证据约束
- 它兼容后续升级，可以在高价值问题上逐步下沉出更重的锚点页、claim 页和 patch 分析页

换句话说，首版最正确的目标不是“把所有源码整理完”，而是“让 `Codex` 从第一天起就能用这套库回答得更稳、更快、更可追溯”。
